# 代码审查工作流 (Code Review Workflow)

本 Skill 规范了对任意项目进行系统化代码审查的标准流程。它指导 AI 代理执行多遍分层 review，融合了 Google Code Review、Conventional Comments、风险驱动审查等业界最佳实践，覆盖架构设计、逻辑缺陷、结构问题、类型安全、格式规范五个维度。

## 前置步骤：项目探测

在执行审查前，先探测项目特征以适配审查策略：

- 识别项目语言和框架（Python/JS/TS/Go/Rust/...）
- 识别包管理器（uv/pip/npm/yarn/pnpm/cargo/...）
- 识别 Lint/Format 工具链（ruff/pylint/eslint/prettier/clippy/...）
- 识别测试框架和运行方式（pytest/vitest/jest/go test/cargo test/...）
- 识别目录结构约定（src/、tests/、docs/ 等）
- 通过 `git diff` / `git log` 确定本次 review 的范围（全量还是增量）

## 审查原则

> "The standard is not perfection, but continuous improvement." — Google Code Review Guidelines

### 核心理念

1. **正向改进优先**：审查的目的是提升代码整体健康度，而非追求完美。只要变更明显改善了代码质量，就应批准。
2. **难以 review = 难以维护**：如果一段代码审查时难以理解，未来维护时也会是麻烦。复杂度本身就是一种缺陷。
3. **Boy Scout Rule（童子军规则）**：每次提交应让代码比之前更干净一点。不要求一次性清理所有历史债务，但不能新增债务。
4. **自审先行**：提交者应在请求 review 前自行过一遍 diff，标注关键决策点和风险区域。
5. **具体优于笼统**：反馈应包含「什么情况下会出问题」「为什么这样有问题」「建议如何改进」，而非仅说「这里不对」。

### 审查金字塔（分配精力的优先级）

```
         ┌─────────┐
         │  风格   │ ← 交给工具（lint/format），人工少花时间
         ├─────────┤
         │  设计   │ ← 模块边界、抽象层次、数据流
         ├─────────┤
         │ 正确性  │ ← 逻辑缺陷、边界条件、并发安全
         ├─────────┤
         │ 安全性  │ ← 注入、权限、敏感数据、依赖风险
         ├─────────┤
         │ 测试    │ ← 覆盖关键路径、边界用例、可维护性
         └─────────┘
```

越底层越重要，应分配越多精力。风格问题交给自动化工具，人的精力集中在安全性和正确性上。

### 风险驱动的审查密度

对以下高风险区域，审查力度加倍：

| 风险级别 | 代码特征 | 审查密度 |
|---------|---------|---------|
| 🔴 极高 | 认证/授权、支付/交易、数据迁移、加密操作、SQL 拼接 | 逐行审查 + 手动验证 |
| 🟠 高 | 状态管理、并发/异步、外部 API 调用、配置变更 | 逐段审查 + 边界推演 |
| 🟡 中 | 业务逻辑、数据处理、UI 组件 | 逻辑审查 + 已有测试验证 |
| 🔵 低 | 纯重构（无行为变更）、文档、样式 | 抽查 + 自动化检查 |

## 审查流程

```
Pass 0: 架构 + 设计（最先执行——只看 diff 上下文 + 模块边界）
├── 高内聚低耦合：一个模块是否做了太多事？能否拆成 2-3 个小模块？
├── 封装完整性：私有函数被跨模块引用？配置读取散落在各处？
├── 数据流清晰度：同一个概念（如 results 对象）是否在不同层有统一的结构？
├── 抽象层次：是否有遗漏的抽象层？或过度抽象（过度工程化）？
├── 硬编码审计：魔法数字、魔法字符串、路径硬编码假设
├── 循环依赖：import/require 关系是否形成环？
├── 死代码：废弃的功能、未使用的 class/id、空的回调
├── 技术债务：旧设计残留（已废弃的概念/API 但代码还在引用）
├── 单一数据源：同一个常量是否在多个位置定义？事件类型是否散落各处？
└── 模块边界：功能划分是否明显？不同职责是否混在一个文件里？

Pass 1: 逻辑 + Bug（逐行审查——最耗时的 pass）
├── 死代码、未使用变量/导入
├── 参数未使用、函数签名不一致
├── 边界条件（空列表、除零、null/None/undefined 传播、负值、极值）
├── 可变默认值陷阱（list/dict/对象作为默认参数，每次调用共享同一实例）
├── 并发/异步陷阱（竞态条件、死锁、goroutine 泄漏、Promise 未 await）
├── 错误处理完整性（异常是否被静默吞掉？错误信息是否足够诊断？）
├── 资源管理（文件句柄、连接、定时器是否正确释放？）
└── 日期/时间/时区处理是否正确

Pass 2: 结构 + 组织
├── 巨石文件拆分（>300 行考虑拆分，>500 行必须给出理由）
├── 巨石函数拆分（>50 行考虑提取子函数，圈复杂度 >10 重点审查）
├── 重复代码提取公共函数/组件
├── 模块职责单一性（一个模块只做一件事）
├── 导入顺序（标准库 → 第三方 → 本地；类型导入单独成组）
├── 模块导出完整性（__init__.py / index.ts 等）
└── 命名质量（是否自解释？是否与领域术语一致？是否有误导性缩写？）

Pass 3: 类型 + 文档
├── 函数签名类型注解（Python type hints / TypeScript types / 等）
├── 返回类型注解（含 Optional/Union/nullable，避免泛型滥用）
├── docstring/JSDoc 完整性（参数、返回值、异常、使用示例）
├── 注释质量（注释应解释「为什么」，而非「做了什么」）
├── 注释与代码一致性（过时注释比没注释更糟糕）
├── 文档与代码一致性（README 是否反映最新架构）
└── API 契约是否清晰（公共接口的输入输出是否明确）

Pass 4: Lint + Format（自动化——人工做最后的确认）
├── 运行项目的 lint 工具
├── 运行项目的 format 工具
├── 检查 CI 配置是否包含 lint/format/test 步骤
└── 修复所有可自动修复的问题
```

## 各语言重点关注

### Python
- 可变默认值 `def f(l=[])`
- `is` vs `==` 语义混淆
- `__del__` 的不可靠性
- 生成器/迭代器提前耗尽
- `with` 语句遗漏（文件/锁未释放）
- `async/await` 混用导致事件循环阻塞
- `MutableMapping` / `Sequence` 等 ABC 接口传参

### JavaScript / TypeScript
- `==` 隐式类型转换（始终用 `===`）
- `this` 绑定丢失（回调中未 bind/未用箭头函数）
- `undefined` vs `null` 语义混淆
- `Promise` 未 `await` / 未 `.catch`
- `useEffect` 依赖数组遗漏或闭包过期（React）
- `any` 类型滥用（TypeScript）
- `prototype pollution` 风险

### Go
- goroutine 泄漏（无 context 取消/无 channel 关闭）
- nil pointer dereference（未检查 error 直接使用返回值）
- defer 在循环中堆积（应封装到函数中）
- slice append 后旧 slice 仍被引用
- channel 死锁（无缓冲 channel 无人接收）

### Rust
- `unwrap()` / `expect()` 在生产代码中使用
- `unsafe` 块缺少安全注释
- 生命周期标注缺失或不正确
- `clone()` 滥用（应使用引用）
- `Rc` / `Arc` 循环引用导致内存泄漏

### 通用
- 硬编码密钥/Token/密码
- 日志中泄露敏感信息（手机号、密码、Token）
- 第三方依赖引入了不必要的重量级包
- `toString()` / `str()` 用于展示逻辑而非调试

## 审查反馈规范

每次发现的问题按照以下格式输出，区分严重程度：

### 严重程度

| 标记 | 含义 | 说明 |
|------|------|------|
| 🔴 **blocker** | 阻断 | 必须修复才能合并：崩溃、数据丢失、安全漏洞、核心功能失败 |
| 🟠 **major** | 重要 | 应该在合并前修复：性能问题、缺少关键测试、错误处理缺失 |
| 🟡 **minor** | 小优化 | 建议修复但可后置：代码风格、命名优化、注释补充 |
| 🔵 **nit** | 建议 | 完全可选：个人偏好、替代方案探讨 |
| 🟢 **praise** | 表扬 | 正向反馈：好的设计、巧妙的实现、清晰的命名 |

### 反馈模板

每个问题遵循「具体问题 → 影响 → 建议」三段式结构：

```
[严重程度] 文件:行号 — 问题简述

影响：描述什么场景下会出问题、严重程度如何

建议：给出具体的替代方案和代码示例

```

### 示例

```
[🔴 blocker] src/auth/login.ts:42 — 密码明文记录到日志

影响：`console.log` 会输出用户密码，任何能看到日志的人（运维、开发、
日志平台）都能获取用户凭据，严重安全事故

建议：移除该日志，或仅记录登录尝试的 user_id（不含密码）：
  - console.log(`User ${password} logged in`)
  + logger.info(`Login attempt for user: ${userId}`)
```

## 审查清单

每次 review 完成后逐项确认：

### 自动化检查
- [ ] 测试套件全部通过（无失败、无误报）
- [ ] Lint 检查全部通过（无 warning、无 error）
- [ ] Format 检查无 diff（代码已格式化）
- [ ] CI 流水线配置包含以上检查（如无可建议添加）

### 安全
- [ ] 无硬编码密钥/Token/密码
- [ ] 无敏感信息输出到日志或错误消息
- [ ] SQL/命令均使用参数化，无字符串拼接
- [ ] 用户输入有验证和清理
- [ ] 权限检查在每个敏感操作前执行

### 正确性
- [ ] 无 `unwrap()` / `panic` 等在生产路径上的强制崩溃
- [ ] 无死代码、无未使用导入、无废弃样式/class
- [ ] 无调试输出残留（`print` / `console.log` / `dbg!` 等）
- [ ] 无循环依赖、无跨模块私有函数引用
- [ ] 边界条件已处理（空输入、null/None、除零、负值、极值）
- [ ] 并发/异步代码无竞态条件
- [ ] 错误被恰当处理，不会被静默吞掉
- [ ] 资源（连接、文件、定时器）在异常路径上也正确释放

### 测试
- [ ] 新增功能有对应测试覆盖
- [ ] 测试覆盖了 happy path 和至少一个错误/边界路径
- [ ] 每个测试的断言值与方法实际行为一致（不是「恰好通过」而是「正确验证」）
- [ ] 删除功能时，相关测试同步删除或更新

### 设计
- [ ] 配置项不硬编码（通过配置文件或环境变量读取）
- [ ] 常量/枚举/事件类型有单一定义源
- [ ] 模块职责单一，不混入无关关注点
- [ ] 公共接口/API 契约清晰稳定

### 一致性
- [ ] 修改函数签名 → 所有调用处和测试同步更新
- [ ] 修改 API（prop/参数名）→ 相关文档和类型定义同步更新
- [ ] 文档（README / API docs）反映最新设计和接口
- [ ] 命名与项目已有风格一致（不引入新的命名约定）

### 可维护性
- [ ] 复杂逻辑有注释解释「为什么」，而非「做了什么」
- [ ] 所有公共函数有类型注解和文档注释
- [ ] 无超过 300 行的文件（或超过者有合理理由）
- [ ] 硬核理解的代码段有注释或文档链接
- [ ] 第三方依赖引入合理（无重复功能、无过度体积）

## 常见问题速查

| 问题 | 修复 |
|------|------|
| 导入顺序问题 | 如因副作用必须先于正常导入，加对应的 lint ignore 注释 |
| 未使用导入/变量 | 删除或以下划线/前缀标记 |
| 可变默认值 | `def f(x=[])` → `def f(x=None)` + 内部初始化 |
| 循环导入 | 提取共享定义到独立的 `types.py` / `constants.ts` 等 |
| 私有函数跨模块 | 改名去掉私有标记或暴露公开 API |
| 事件类型/常量散落 | 定义统一的常量/枚举文件，所有模块引用它 |
| 配置硬编码 | 写入配置文件（toml/yaml/json/env），通过统一入口读取 |
| 调试输出残留 | 替换为项目日志模块的统一调用，确保有合适的日志级别 |
| 文档-代码-测试不一致 | 修改后立即跑测试验证，函数签名变更 → 同步更新调用处和测试 |
| 测试恰好通过但实际是错的 | 检查断言值是否真的等于代码返回值（不要靠巧合） |
| 缺少测试覆盖 | 新增公开函数/模块至少要有基本的导入和核心逻辑测试 |
| Git 暂存区有未提交变更 | review 前确认工作区干净，或明确本次 review 的范围 |
| 异步函数未 await | 检查所有返回 Promise 的调用；TypeScript 开启 `no-floating-promises` |
| goroutine 泄漏 | 确保所有 goroutine 有退出机制（context 取消或 channel 关闭） |
| `unwrap()` 在生产代码 | 替换为 `?` 操作符或 `expect("说明")` 并记录错误上下文 |
| 日志泄密 | 编写日志脱敏函数，自动遮蔽手机号/邮箱/密码/Token |
| 过度 fetch/重绘 | 使用 debounce/throttle，检查 React 组件重渲染频率 |

## 增量审查 vs 全量审查

根据变更规模选择审查策略：

| 变更类型 | 典型场景 | 审查策略 |
|---------|---------|---------|
| 小 PR（<100 行） | Bug 修复、小功能 | Pass 1-2 为主，Pass 0 快速扫描 |
| 中 PR（100-500 行） | 新功能、重构 | 完整 Pass 0-4，聚焦新增代码 |
| 大 PR（>500 行） | 大功能、架构变更 | 建议拆分成小 PR；如不可拆，Pass 0 优先，确保设计正确再深入细节 |
| 全量审查 | 接手新项目、安全检查 | 完整 Pass 0-4，重点关注安全和架构风险 |
| 热修复 | 线上紧急修复 | Pass 1 为核心（逻辑+安全），Pass 2-4 后置到常规 PR |

## CI/CD 集成建议

审查完成后，向项目建议添加以下 CI 检查（如尚未配置）：

- **Lint 检查**：在每次 push/PR 时自动运行
- **类型检查**：TypeScript (`tsc --noEmit`)、Python (`mypy`/`pyright`)、Go (`go vet`)
- **测试**：单元测试 + 集成测试自动运行
- **安全扫描**：依赖漏洞扫描（`pip-audit`/`npm audit`/`cargo audit`）、密钥泄露检测
- **代码覆盖率**：设置最低覆盖率阈值，防止新代码不写测试
- **格式化检查**：确保代码风格一致（`ruff format --check`/`prettier --check`）

## 审查完成后输出

审查结束生成一份结构化报告：

```
## Code Review Report

### 概览
- 审查范围：[文件列表 / git diff 摘要]
- 变更类型：[feature / bugfix / refactor / hotfix / ...]
- 审查策略：[增量 / 全量]
- 风险等级：🔴极高 / 🟠高 / 🟡中 / 🔵低

### 发现汇总
- 🔴 blocker: N 个
- 🟠 major: N 个
- 🟡 minor: N 个
- 🔵 nit: N 个
- 🟢 praise: N 个

### 详细发现
（按严重程度排列，每个问题按反馈模板输出）

### 总结
- 是否建议合并：[是 / 修复 blocker 后合并 / 修复 major 后合并 / 否]
- 整体代码健康度变化：[↑ 提升 / → 持平 / ↓ 下降]
- CI 配置建议（如有）
- 关键风险点（如有）
```
